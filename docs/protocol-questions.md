# Открытые вопросы протокола

Документ перечисляет то, что мешает перевести спецификацию из состояния `draft`,
и указывает, каким наблюдением закрывается каждый пункт. Установленные факты
лежат в [observations.md](observations.md).

Пункт считается закрытым, когда наблюдение выполнено и результат записан в
`observations.md` с указанием файла, по которому его можно проверить.

## 1. Есть ли устойчивая позиция для переигрывания событий

**Почему это важнее остального.** Гарантия доставки `at-least-once` держится на
существовании позиции, с которой можно запросить пропущенное. Если позиции нет,
раздел о событиях переписывается вокруг сверки состояния, а это изменение
контракта, а не реализации: меняются подписи операций и смысл курсора. Такое
изменение после публикации версии 1.0 обошлось бы в мажорный выпуск шести SDK.

**Что известно.** На странице чата есть два кандидата разной природы:

* десятизначные числа `data-node-msg` и `data-user-msg` на каждом диалоге -
  похожи на идентификаторы сообщений;
* восьмизначные строки `data-chat`, `data-orders`, `data-bookmarks-tag` -
  похожи на метки состояния.

Разница принципиальная. Монотонный идентификатор отвечает на вопрос «что я
пропустил». Метка состояния отвечает только на вопрос «изменилось ли что-нибудь»
и для переигрывания непригодна.

**Чем закрывается.** Двумя чтениями `/chat/` с изменением между ними.

```bash
D:\Funora\Funora-python\.venv\Scripts\python.exe -m funora.observe /chat/ --compare
```

Инструмент прочитает страницу, попросит сделать изменение и нажать Enter, затем
прочитает её ещё раз и напечатает, что изменилось. Значения сравниваются в
памяти и на диск не попадают; в выводе только характер изменения и величина
шага. Файлов режим не создаёт.

Подходящее изменение - любое из двух:

* открыть непрочитанную переписку в браузере: должно измениться `data-user-msg`,
  но не `data-node-msg`;
* получить сообщение от собеседника: должно вырасти `data-node-msg`.

Как читать результат:

| Что показал отчёт | Вывод |
|---|---|
| `data-node-msg выросло на N` | идентификатор монотонный, позиция для переигрывания есть, гарантия `at-least-once` остаётся |
| `data-node-msg изменилось` без шага | значение не числовое, это метка состояния |
| `data-chat изменилось`, шага нет | метка состояния, для переигрывания непригодна |
| `data-user-msg выросло`, `data-node-msg` нет | подтверждается разделение «прочитано» и «последнее» |

## 2. Есть ли структурный признак системного сообщения

**Почему это важно.** Если системное сообщение об оплате отличается от обычного
только текстом, покупатель может отправить сообщение с таким же текстом и
получить товар от бота, который доверяет тексту. Это не теоретическая уязвимость,
а прямое следствие устройства разметки.

**Что известно.** В снимке `/chat/` открытой переписки нет: страница показана в
состоянии `chat-not-selected`. Классов вида `system`, `service`, `notification`
на ней не встречается.

**Чем закрывается.** Снимок страницы конкретной переписки, в которой есть хотя бы
одно системное сообщение.

```bash
D:\Funora\Funora-python\.venv\Scripts\python.exe -m funora.observe "/chat/?node=НОМЕР" --out observations --locale ru
```

Номер диалога виден в адресной строке браузера при открытой переписке.

## 3. Соответствие статусов заказа классам

**Что известно.** Статус несётся двумя структурными признаками: модификатором на
строке (`tc-item info`) и цветовым классом на ячейке (`tc-status text-primary`).
В снимке все три заказа в одном состоянии, поэтому известна одна пара.

**Чем закрывается.** Снимок `/orders/trade` в момент, когда заказы находятся в
разных состояниях. Отдельного действия не требует - достаточно повторить снимок
позже.

**Что делать до этого.** Перечисление статусов остаётся открытым, с обязательным
запасным значением для незнакомого. Закрывать его по одному наблюдению нельзя.

## 4. Как выглядят блокировка и страница проверки

**Что известно.** Истёкшая сессия наблюдалась и распознаётся уверенно. Страница
проверки и страница блокировки - нет.

Признаки `challenge_widget`, `challenge_text`, `blocked_text`, `maintenance_text`
в `DEFAULT_SIGNATURES` помечены `provisional=True`. Помета означает, что признак
составлен умозрительно: таких страниц мы не видели, и вердикт по ним требует
ручного подтверждения.

**Чем закрывается.** Наблюдением, которое нельзя запланировать и нельзя
вызывать намеренно: вызвать блокировку означало бы намеренно нарушить правила
площадки. Признаки остаются помеченными до тех пор, пока такая страница не
встретится в обычной работе.

## Чего мы не будем выяснять

Пункты ниже закрыты не потому, что ответ известен, а потому что выяснять их
нельзя.

* Пороги ограничения частоты запросов. Их измерение означает намеренное
  превышение. Бюджеты в `spec/runtime/budget.yaml` остаются провизорными и
  подбираются консервативно.
* Поведение страницы проверки. Вызывать её намеренно нельзя.
* Что-либо, требующее второго аккаунта, созданного ради наблюдения.
