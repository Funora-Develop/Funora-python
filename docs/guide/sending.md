# Отправка сообщений

Это единственная операция записи, которая работает. И это единственная глава
руководства, где ошибка стоит денег и репутации, - поэтому она длиннее
остальных.

```python
from funora import Client, EnvSecretProvider

with Client(EnvSecretProvider()) as client:
    result = client.chats.send_text("123456", "Здравствуйте! Товар выдан.")
    print(result.outcome, result.reason)
```

## Исходов три, а не два

```python
from funora.send_outcome import SendOutcome

SendOutcome.CONFIRMED    # площадка подтвердила: сообщение в диалоге
SendOutcome.REFUSED      # площадка отказала, сообщения нет
SendOutcome.UNCONFIRMED  # неизвестно
```

Третий исход - главное здесь. Ответ мог не дойти, соединение оборваться,
площадка ответить неразборчиво. Сообщение при этом **могло уйти**, а могло и
нет.

!!! danger "Повторная отправка при `UNCONFIRMED` - это второе сообщение покупателю"

    Самый частый способ испортить себе репутацию автоматикой: покупатель
    получает одно и то же дважды, а иногда трижды.

## Правило вызывающего

**Исключение означает, что сообщение не ушло.** Возврат значения означает, что
исход - в этом значении, и его нужно прочитать.

```python
from funora import Client, EnvSecretProvider
from funora.send_outcome import SendOutcome

with Client(EnvSecretProvider()) as client:
    result = client.chats.send_text("123456", "Товар выдан.")

    if result.outcome is SendOutcome.CONFIRMED:
        mark_delivered()
    elif result.outcome is SendOutcome.REFUSED:
        # Не ушло. Повторять безопасно.
        retry_later(reason=result.reason)
    else:
        # Не известно. Повторять НЕЛЬЗЯ без проверки.
        check_manually(result)
```

## Сверка

При `UNCONFIRMED` SDK не оставляет вас наедине с неизвестностью: он перечитывает
переписку и ищет своё сообщение.

```python
print(result.reconciled)
```

| Значение | Что означает |
|---|---|
| `not_attempted` | сверка не понадобилась - исход был определён сразу |
| `delivered` | сообщение найдено в переписке: оно ушло |
| `absent_from_history` | сообщения в переписке нет |
| `undetermined` | сверка не дала ответа |

Сверка читает переписку трижды, с нарастающими задержками: 1, 3 и 8 секунд.
Числа не выдуманы на месте - они записаны в контракте и одинаковы во всех
реализациях.

!!! warning "`absent_from_history` - не «точно не ушло»"

    Это «в прочитанной переписке его нет». Сообщение могло не успеть появиться,
    страница могла отдаться из кэша. Отрицательного вердикта сверка не выносит
    нарочно: он подтолкнул бы к повтору, а повтор здесь и есть та ошибка,
    которую всё это устройство предотвращает.

## Почему `reason` - строка, а не текст для человека

Неполный ответ действия с отсутствующим `response.error` даёт
`unconfirmed / response_error_missing`. Дубли JSON-ключей, неконечные числа
и ошибки декодирования дают `unconfirmed / body_not_json`. Текстовая отправка
может затем свериться с историей по обычному расписанию; повторной отправки
из-за такого ответа нет. Только явный `error: null` позволяет перейти к
проверке положительного подтверждения в нужном диалоге.

```python
print(result.reason)  # например, confirmed_by_channel
```

Причины перечислены закрытым списком в контракте: `confirmed_by_channel`,
`channel_reported_error`, `body_not_json`, `node_mismatch`, `empty_message_list`
и ещё несколько. Все они машиночитаемы и годятся для `if`.

Человеческий текст меняется от версии к версии, и код, написанный на нём,
ломается молча.

## Темп: сколько можно писать

У отправки свой ограничитель, отдельный от общего бюджета. Он считает не «сколько
запросов в секунду», а **сколько разных собеседников** вы трогаете.

Причина простая: площадка терпимо относится к активной переписке с теми, кто вам
уже писал, и совсем иначе - к рассылке по тем, кто не писал.

```python
result = client.chats.send_text("123456", "Здравствуйте!", declared_cold=True)
```

`declared_cold=True` - это ваше заявление: «пишу первым, собеседник мне не
писал». У таких обращений отдельный, гораздо более узкий счёт и окно длиной в
сутки.

!!! note "Признак ставит вызывающий, но холодность определяет SDK"

    «Холодная» переписка - та, по которой ограничитель не видел входящего
    сообщения. Определяет он это сам, и если переписка холодная, а признак не
    поставлен, отправка **отказывает** с `cold_outreach_not_declared`. Ждать тут
    бесполезно: признак ставите вы.

    Обратное послабления не даёт: заявленное холодным тёплым не станет.

!!! tip "Ответ покупателю холодным обращением НЕ является"

    Переписка становится тёплой, когда цикл наблюдения видит в ней входящее
    сообщение. Поэтому автоответчику `declared_cold` не нужен: покупатель
    написал сам, и действует предел в тридцать сообщений в час, а не три
    обращения в сутки.

    Как это выглядит целиком - в главе [Бот](bot.md).

    Работает это только под наблюдением: греет переписку сам цикл. Разовый
    скрипт, который просто позвал `send_text`, наблюдения не вёл и потому о
    входящем сообщении не знает - для него переписка холодная.

При превышении приходит отказ, а не пауза: SDK не будет молча спать за вас
неизвестно сколько. Подробности - в главе [Темп и бюджет](budget.md).

!!! warning "Пределы считаются по долговечному реестру, и без него отправки нет"

    Реестр отправок лежит в файле состояния и переживает перезапуск. Часовая
    квота остаётся часовой: бот, падающий и поднимаемый супервизором, не
    получает тридцать сообщений на каждый запуск.

    Отсюда требование к вызову: **без `state_path` отправка отказывает**. Отказ
    громкий - `ConfigurationError`, - а не молчаливое послабление, потому что
    реестр в памяти выглядит защитой и ею не является.

    ```python
    with Client(EnvSecretProvider(), state_path="funora-state.json") as client:
        client.chats.send_text(node_id, "здравствуйте")
    ```

    Снять это требование можно, и снимается оно только явно - именованной
    настройкой с приставкой `unsafe_`, которая вдобавок оставляет отметку в
    состоянии здоровья. Снять защиту незаметно нельзя.

При повреждении раздела `outbound` создание клиента или подключение
`watch(state_path=...)` завершается `StateSchemaIncompatibleError` до сети.
SDK не пропускает испорченные попытки и не превращает строки, числа и `null`
в пустой журнал. Ошибка подключения сохраняет прежнюю квоту и признак
долговечности; после восстановления файла можно повторить вызов тем же клиентом.

Корректные файлы v6 продолжают читаться без миграции. Отсутствующий раздел
старого файла означает пустой журнал, а отсутствующий `cold` у старой попытки
считается `True`. При подключении журнала к работающему клиенту сохраняются
монотонные метки накопленных попыток и наиболее свежие отметки входящих.

## Чего в этой главе нет

Отправки изображения (`chats.send_image`) - запроса, которым площадка
загружает файл, никто не наблюдал. Отметки прочитанным (`chats.mark_read`) -
то же самое.


## Сбой после отправки

Потерянный ответ транспорта возвращается как `SendOutcome.UNCONFIRMED` с
причиной `transport_error`. Неподходящий HTTP-статус даёт
`unexpected_http_status`. Автоматического повторения сообщения нет.
Операция чтения до отправки по-прежнему может завершиться исключением.

Отправка изображений использует тот же долговечный журнал и тот же
ограничитель, что отправка текста. Для первого сообщения покупателю передайте
`declared_cold=True`, если переписка холодная. Без `state_path` отправка
отказывается до загрузки изображения. Загрузка и отправка учитываются как два
запроса.
