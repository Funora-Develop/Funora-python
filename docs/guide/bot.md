# Бот: отвечаем на сообщения

Здесь собирается то, ради чего обычно и берут такой SDK: пришло сообщение -
бот его прочитал, проверил и ответил.

```python
from funora import Client, EnvSecretProvider, EventType, Router

router = Router()

with Client(EnvSecretProvider()) as client:

    @router.on(EventType.MESSAGE_CREATED)
    def answer(event) -> None:
        """Отвечает на сообщение покупателя.

        Аргументы:
            event (Event): Событие о новом сообщении.

        Возвращает:
            None
        """
        if event.payload["direction"] != "inbound":  # (1)!
            return

        thread = client.chats.thread(event.payload["chat_id"])  # (2)!
        last = thread.messages()[-1]
        if not last.text.is_observed:
            return

        if last.text.value.strip().lower() == "!цена":
            client.chats.send_text(event.payload["chat_id"], "Прайс: 100 рублей за штуку.")

    client.watch(router)
```

1. **Самая важная строка во всём примере.** Без неё бот отвечает на собственный
   ответ, тот приходит новым сообщением, бот отвечает снова - и переписка
   уходит в петлю до упора в часовой предел.
2. Текста в событии нет, и это не упущение: нагрузка события - указатель на
   сущность, а не её копия. Событие уходит в журнал, в очередь, в чужую
   систему, и нести туда чужую переписку незачем. Кому нужен текст, тот читает
   страницу сам и знает, что делает.

## Направление сообщения

У каждого события о новом сообщении есть `direction`:

| Значение | Что означает |
|---|---|
| `inbound` | написал собеседник |
| `outbound` | написали мы сами |
| `unknown` | определить не удалось |

Определяется оно **структурно**: сравнением адреса профиля автора с адресом
собственного профиля, снятым с той же страницы. Не по имени - имя меняется, и
совпадение имён подделывается собеседником, назвавшимся как продавец.

!!! warning "`unknown` - это не третье направление"

    Это честное незнание: адрес собственного профиля со страницы не снялся либо
    у сообщения не наблюдалось автора. Считать такое сообщение входящим нельзя,
    и SDK так не делает.

## Почему автоответ вообще проходит

У отправки есть [ограничитель](sending.md#_5): в холодную переписку - ту, где
собеседник вам не писал, - можно обратиться три раза в сутки, и только объявив
обращение холодным явно.

Переписка становится **тёплой**, когда цикл наблюдения видит в ней входящее
сообщение. Ровно поэтому пример выше не передаёт `declared_cold`: покупатель
написал сам, переписка тёплая, и действует предел в тридцать сообщений в час.

!!! note "Греет только входящее и только сообщение"

    Событие об изменении диалога не греет: счётчик непрочитанного двигает и
    наша собственная отправка, и ограничитель, гревшийся на нём, отменял бы сам
    себя - первая отправка в холодную переписку делала бы её тёплой.

    Заказ тоже не греет: покупка означает, что человек что-то купил, а не что
    он готов к переписке.

## Одно и то же событие может прийти дважды

Доставка объявлена **как минимум однократной**. Обработчик, упавший на событии,
оставляет курсор на месте, и то же событие придёт снова - это защита от потери,
а не ошибка.

Отсюда правило: **обработчик обязан быть идемпотентным**. Отличить повтор от
нового события можно по номеру попытки:

```python
@router.on(EventType.MESSAGE_CREATED)
def answer(event) -> None:
    """Отвечает один раз.

    Аргументы:
        event (Event): Событие.

    Возвращает:
        None
    """
    if event.delivery.attempt > 1:
        return  # это повтор, мы уже отвечали
```

Надёжнее - хранить свой признак «на это событие уже отвечено» рядом с
состоянием бота: номер попытки живёт в памяти процесса и обнуляется
перезапуском.

## Обработчик может звать операции

Вызов `client.chats.thread(...)` и `client.chats.send_text(...)` прямо из
обработчика работает: обработчики выполняются в том же потоке, что и цикл, и
клиент этого не запрещает.

!!! danger "Но у этого есть цена, и её надо знать"

    Каждый вызов из обработчика - это запросы **внутри шага**. Шаг растягивается,
    опрос стоит. Отправка с последующей сверкой может добавить к шагу до
    двенадцати секунд: сверка читает переписку трижды с паузами.

    А главное - отказ, вылетевший из обработчика, считается отказом обработчика:
    курсор не сдвинется, и то же событие придёт снова. Ловите отказы сами:

    ```python
    from funora import FunoraError

    try:
        client.chats.send_text(chat_id, text)
    except FunoraError as error:
        log.error("не ответили: %s", error)
    ```

## Писать из другого потока нельзя

`Client` не защищён ни одной блокировкой. Бюджет, ограничитель исходящих и
состояние сессии - обычные изменяемые объекты, и проверка с последующей записью
у них не атомарна.

Практически это значит: **телеграм-бот в отдельном потоке не может позвать
`client.chats.send_text` напрямую**. Гонка проявится не отказом, а недосчётом
ограничителя - то есть превышением настоящего предела площадки, и узнаете вы об
этом от площадки.

Пока для этого нет отдельного механизма, единственный безопасный способ - чтобы
отправку выполнял тот же поток, что и наблюдение: сложить задание в свою очередь
и разобрать её из обработчика.

## Чего у этого бота не будет

Стоит прочитать до того, как строить планы.

**Автовыдачи товара нет и не планируется в ближайшем.** Три независимые причины,
каждой хватило бы одной: событие о заказе не несёт ни названия лота, ни
идентификатора предложения, и `OrderView` их тоже не содержит; состояний заказа
читается два из скольких-то, и заказ в возврате даёт ненаблюдённое значение;
порядок между событием об оплате и событием о заказе не гарантирован - у них
разные ключи упорядочивания.

Честное, что можно сделать, - уведомить и предложить оператору подтвердить.

**Управления лотами нет.** Ни поднятия, ни включения, ни смены цены: запросов,
которыми площадка это делает, никто не наблюдал.

**Скорость реакции ограничена.** Читается список диалогов, потом до пяти
переписок за шаг. Если разом написали двадцать покупателей, последний получит
ответ через четыре шага.

**Рассылки не будет.** Тридцать сообщений в час, пятнадцать собеседников в час,
тридцать секунд между сообщениями в одну переписку. Ограничитель при
превышении **отказывает**, а не ждёт.

Подробнее - в [Что Funora сегодня не может](../limits.md).
