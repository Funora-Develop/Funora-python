# Бот: отвечаем на сообщения

Здесь собирается то, ради чего обычно и берут такой SDK: пришло сообщение -
бот его прочитал, проверил и ответил.

```python
from funora import Client, EnvSecretProvider, EventType, Router

router = Router()

with Client(EnvSecretProvider()) as client:

    @router.on(EventType.MESSAGE_CREATED)
    def answer(event) -> None:
        """Отвечает на сообщение покупателя.

        Аргументы:
            event (Event): Событие о новом сообщении.

        Возвращает:
            None
        """
        if event.payload["direction"] != "inbound":  # (1)!
            return

        thread = client.chats.thread(event.payload["chat_id"])  # (2)!
        last = thread.messages()[-1]
        if not last.text.is_observed:
            return

        if last.text.value.strip().lower() == "!цена":
            client.chats.send_text(event.payload["chat_id"], "Прайс: 100 рублей за штуку.")

    client.watch(router)
```

1. **Самая важная строка во всём примере.** Без неё бот отвечает на собственный
   ответ, тот приходит новым сообщением, бот отвечает снова - и переписка
   уходит в петлю до упора в часовой предел.
2. Текста в событии нет, и это не упущение: нагрузка события - указатель на
   сущность, а не её копия. Событие уходит в журнал, в очередь, в чужую
   систему, и нести туда чужую переписку незачем. Кому нужен текст, тот читает
   страницу сам и знает, что делает.

## Направление сообщения

У каждого события о новом сообщении есть `direction`:

| Значение | Что означает |
|---|---|
| `inbound` | написал собеседник |
| `outbound` | написали мы сами |
| `unknown` | определить не удалось |

Определяется оно **структурно**: сравнением адреса профиля автора с адресом
собственного профиля, снятым с той же страницы. Не по имени - имя меняется, и
совпадение имён подделывается собеседником, назвавшимся как продавец.

!!! warning "`unknown` - это не третье направление"

    Это честное незнание: адрес собственного профиля со страницы не снялся либо
    у сообщения не наблюдалось автора. Считать такое сообщение входящим нельзя,
    и SDK так не делает.

## Почему автоответ вообще проходит

У отправки есть [ограничитель](sending.md#_5): в холодную переписку - ту, где
собеседник вам не писал, - можно обратиться три раза в сутки, и только объявив
обращение холодным явно.

Переписка становится **тёплой**, когда цикл наблюдения видит в ней входящее
сообщение. Ровно поэтому пример выше не передаёт `declared_cold`: покупатель
написал сам, переписка тёплая, и действует предел в тридцать сообщений в час.

!!! note "Греет только входящее и только сообщение"

    Событие об изменении диалога не греет: счётчик непрочитанного двигает и
    наша собственная отправка, и ограничитель, гревшийся на нём, отменял бы сам
    себя - первая отправка в холодную переписку делала бы её тёплой.

    Заказ тоже не греет: покупка означает, что человек что-то купил, а не что
    он готов к переписке.

## Одно и то же событие может прийти дважды

Доставка объявлена **как минимум однократной**. Обработчик, упавший на событии,
оставляет курсор на месте, и то же событие придёт снова - это защита от потери,
а не ошибка.

Отсюда правило: **обработчик обязан быть идемпотентным**. Отличить повтор от
нового события можно по номеру попытки:

```python
@router.on(EventType.MESSAGE_CREATED)
def answer(event) -> None:
    """Отвечает один раз.

    Аргументы:
        event (Event): Событие.

    Возвращает:
        None
    """
    if event.delivery.attempt > 1:
        return  # это повтор, мы уже отвечали
```

Надёжнее - хранить свой признак «на это событие уже отвечено» рядом с
состоянием бота: номер попытки живёт в памяти процесса и обнуляется
перезапуском.

## Обработчик может звать операции

Вызов `client.chats.thread(...)` и `client.chats.send_text(...)` прямо из
обработчика работает: обработчики выполняются в том же потоке, что и цикл, и
клиент этого не запрещает.

!!! danger "Но у этого есть цена, и её надо знать"

    Каждый вызов из обработчика - это запросы **внутри шага**. Шаг растягивается,
    опрос стоит. Отправка с последующей сверкой может добавить к шагу до
    двенадцати секунд: сверка читает переписку трижды с паузами.

    А главное - отказ, вылетевший из обработчика, считается отказом обработчика:
    курсор не сдвинется, и то же событие придёт снова. Ловите отказы сами:

    ```python
    from funora import FunoraError

    try:
        client.chats.send_text(chat_id, text)
    except FunoraError as error:
        log.error("не ответили: %s", error)
    ```

## Писать из телеграм-бота

Это второй вопрос, ради которого такой SDK и берут: ответить покупателю из
телеграма, не заходя на площадку.

Прямо звать `client.chats.send_text` из потока телеграм-бота **нельзя**.
`Client` не защищён ни одной блокировкой: у бюджета и у ограничителя исходящих
проверка с последующей записью не атомарна. Гонка проявится не отказом и не
исключением, а **недосчётом**: ограничитель решит, что за час ушло меньше
сообщений, чем ушло. Объяснит вам это площадка.

Поэтому есть очередь исходящих. Класть в неё можно из любого потока, а
отправляет тот же поток, что ведёт наблюдение, - в паузе между опросами.

```python
import threading

from funora import Client, EnvSecretProvider, EventType, Router
from funora.bot import Bot

router = Router()

with Client(EnvSecretProvider()) as client:
    bot = Bot(client, router)

    def telegram_side() -> None:
        """Изображает обработчик телеграм-бота в своём потоке.

        Возвращает:
            None
        """
        ticket = bot.send(  # (1)!
            "123456",
            "Здравствуйте! Отвечаю из телеграма.",
            idempotency_key="tg-42",  # (2)!
        )
        result = ticket.wait(timeout=60)  # (3)!
        print("исход:", result.outcome if result else "повтор либо не дождались")

    threading.Thread(target=telegram_side, daemon=True).start()
    bot.run()
```

1. Задание кладётся в очередь и вернётся квитанцией. Сама отправка произойдёт
   в потоке наблюдения.
2. Ключ идемпотентности **обязателен**, умолчания у него нет. Отправка
   необратима: лишнее сообщение покупателю не отменить, а перезапуск процесса и
   нажатие кнопки дважды - обычные вещи.
3. Ждать можно из любого потока. Отказ, случившийся в потоке наблюдения,
   бросится здесь: иначе о нём никто бы не узнал.

### Что даёт квитанция

| Что | Когда |
|---|---|
| `ticket.wait(timeout)` | исход отправки либо `None` |
| `ticket.ready` | задание уже отработано |
| `ticket.duplicate` | ключ уже встречался, задание отброшено |

Отказ отправки бросается из `wait()`. Отказ **одного** задания не роняет
наблюдение и не отменяет остальные: цикл не должен вставать из-за чужой кнопки.

### Пределы очереди

За одну паузу разбирается не больше трёх заданий. Предел не про вежливость: одна
отправка при неоднозначном ответе тянет за собой сверку - три чтения переписки с
паузами 1, 3 и 8 секунд. Без предела один разбор растянул бы паузу на минуту, и
всё это время наблюдение стояло бы.

Сама очередь принимает 256 заданий и дальше **отказывает вслух**, а не копит
молча: сообщения, накопленные сверх того, ушли бы с опозданием на часы.

!!! note "Темп опроса от разбора не едет"

    Потраченное на разбор вычитается из паузы, а не добавляется к ней. Иначе чем
    больше работы, тем реже наблюдение - ровно наоборот тому, что нужно: очередь
    наполняется как раз тогда, когда покупатели пишут.

### Из обработчика можно и напрямую

Внутри обработчика события вы уже в потоке наблюдения, и очередь не нужна:

```python
@router.on(EventType.MESSAGE_CREATED)
def answer(event) -> None:
    """Отвечает немедленно.

    Аргументы:
        event (Event): Событие.

    Возвращает:
        None
    """
    bot.send_now(event.payload["chat_id"], "Принято.")
```

`send_now` из чужого потока **отвергается вслух** - `UsageError`. Молчаливая
гонка хуже громкого отказа.

### Из другого процесса - через каталог

Очередь выше живёт **в памяти процесса**, и телеграм-боту, поднятому отдельной
командой, до неё не дотянуться ничем: другой интерпретатор, другая память.

Для этого есть вторая очередь - каталог с файлами. Ни порта, ни базы, ни
запущенного посредника: атомарность даёт сама файловая система.

Со стороны наблюдения:

```python
from funora import Client, EnvSecretProvider, Router
from funora.bot import Bot

with Client(EnvSecretProvider(), state_path="funora-state.json") as client:
    bot = Bot(client, Router(), spool_path="funora-outbox")  # (1)!
    bot.run()
```

1. Каталог создаётся сам. Без этого аргумента его не заводится вовсе: файлы на
   чужом диске без просьбы - это мусор в чужом проекте.

Со стороны телеграм-бота - **другой процесс, другая программа**:

```python
from funora.bot import SendCommand, Spool

spool = Spool("funora-outbox")

accepted = spool.submit(  # (1)!
    SendCommand(
        chat_id="123456",
        text="Здравствуйте! Отвечаю из телеграма.",
        idempotency_key="tg-42",  # (2)!
    )
)

outcome = spool.outcome("tg-42")  # (3)!
if outcome is not None:
    print(outcome.state, outcome.detail)
```

1. `False` означает повтор: задание с таким ключом уже лежит либо уже
   отработано.
2. Ключ становится **частью имени файла**, и потому здесь он строже: латиница,
   цифры, точка, дефис, подчёркивание; по краям - только буква либо цифра.
3. Исход появляется, когда наблюдение задание отработает. `None` означает «ещё
   не дошло», а не «отказ».

### Застрявшее не уходит вторым сообщением

Это главное в каталожной очереди, и ради этого она устроена сложнее, чем
казалось бы нужным.

Задание, взятое в работу процессом, который умер, - это сообщение с
**неизвестной судьбой**. Оно могло уйти на площадку, а могло не уйти: по файлу
этого не видно.

Отправить его снова значит рискнуть вторым сообщением покупателю, а второго не
отменить. Выбросить молча - потерять первое.

Поэтому не делается ни того, ни другого:

```python
stranded = bot.spool.stuck  # ключи, о которых должен решить человек
```

При запуске такие задания переносятся в `stuck/`, оттуда их не берёт никто, и о
них пишется в журнал. Решаете вы, посмотрев переписку, - другого способа узнать
здесь нет.

!!! note "Предел за паузу общий"

    Обе очереди разбираются в один и тот же предел: сперва память, затем
    каталог в остаток. Предел бережёт не очередь, а паузу между опросами - две
    очереди со своими пределами удлинили бы её вдвое.

## Автовыдача

Она есть, и устроена вокруг одной черты: **выдача идёт сама только там, где все
условия выполнены положительно**. Любое незнание - не повод действовать
осторожнее, а повод не действовать: вопрос уходит человеку.

```python
from funora import Client, EnvSecretProvider, Router
from funora.bot import Bot, DeliveryPlan

with Client(EnvSecretProvider(), state_path="funora-state.json") as client:  # (1)!
    bot = Bot(client, Router())

    plan = DeliveryPlan(
        goods={"12345678": "Ваш ключ: ABCD-EFGH-IJKL"},  # (2)!
        chat_of=lambda order_id: client.orders.get(order_id).chat_node_id.value,  # (3)!
    )
    delivery = bot.deliveries(  # (4)!
        plan,
        on_hold=lambda decision: print("руками:", decision.order_id, decision.reason),  # (5)!
    )
```

1. `state_path` **обязателен**. Без него автовыдача отказывает: реестр
   выданного обнулился бы при перезапуске, и товар ушёл бы второй раз по
   заказу, который в списке продаж всё ещё оплачен.
2. Ключ - **идентификатор предложения**, а не название лота. Взять его можно из
   `client.lots.list_own(node_id)`: там он лежит атрибутом строки.
3. Узел диалога есть только на странице заказа, и функцией это сделано нарочно:
   запрос стоит делать лишь тогда, когда всё остальное уже сошлось.
4. **Собирайте через `bot.deliveries()`, а не руками.** Связать реестр с файлом
   состояния можно только через движок, который этот файл открыл; собранная
   руками автовыдача про файл не знает и выглядит рабочей - первый прогон
   отдаёт товар, второй отдаёт его снова.
5. Заказы, которые сами не выдаются, уходят сюда. Без этого они видны только в
   журнале, а журнал читают после происшествия.

### Пять условий выдачи

| Условие | Что означает отказ |
|---|---|
| состояние прочитано и равно `PAID` | `status_not_observed`, `status_not_paid` |
| по заказу ещё не выдавали | `already_delivered` |
| список продаж прочитан полно | `orders_page_incomplete` |
| заказ опознан как **один** лот | `no_offer_matched`, `offer_match_ambiguous` |
| для лота задан товар | `no_goods_for_offer` |

### Как заказ опознаётся, и почему это вывод

Идентификатора предложения в заказе нет: ни строка списка продаж, ни страница
заказа его не несут. Есть только описание - свободный текст, который вы написали
у лота, а площадка показала в заказе.

Ищется **вхождение описания лота в описание заказа**. Не равенство: площадка
дописывает к описанию заказа то, что выбрал покупатель.

!!! danger "Совпало два лота - выдача останавливается"

    Готовые решения той же задачи берут при нескольких совпадениях самое
    длинное описание. Для выдачи товара это выбор наугад, и цена ошибки - чужой
    товар покупателю.

    Исключение ровно одно: если описания вложены друг в друга одной цепочкой
    («Аккаунт Steam» и «Аккаунт Steam с играми»), берётся самое точное. Это не
    выбор наугад - развилки здесь нет.

    Отказ несёт перечень кандидатов: по нему видно, какие лоты неразличимы и
    какой из них стоит переименовать.

Уверенность опознания всегда `Confidence.INFERRED` и никогда не `OBSERVED`:
правило опирается на текст, часть которого пишет покупатель.

### Выдача необратима

Состояние возврата не наблюдалось ни разу, и отменить выдачу нечем. Механизм
односторонний: он выдаёт, но не отзывает.

!!! warning "`paid` - не финансовое подтверждение"

    Оно означает, что площадка показывает состояние оплаты в разделе продаж.
    Отменённым задним числом оно быть может.

### Реестр выдач переживает перезапуск

Курсор заказов защитой от повторной выдачи **не является**: он снимается только
с полного чтения, а события порождаются и по неполному. Поэтому реестр
отдельный, и запись в него идёт **впереди** отправки - и в память, и на диск:
«запишем, когда подтвердится» означает не записать ровно те выдачи, которые
могли уйти.

Лежит он в том же файле состояния, что курсоры и реестр отправок. Владельцев у
файла несколько, и каждый правит свой ключ, не трогая чужих.

## Чего у этого бота не будет

Стоит прочитать до того, как строить планы.

**Управления лотами нет.** Ни поднятия, ни включения, ни смены цены: запросов,
которыми площадка это делает, никто не наблюдал.

**Скорость реакции ограничена.** Читается список диалогов, потом до пяти
переписок за шаг. Если разом написали двадцать покупателей, последний получит
ответ через четыре шага.

**Рассылки не будет.** Тридцать сообщений в час, пятнадцать собеседников в час,
тридцать секунд между сообщениями в одну переписку. Ограничитель при
превышении **отказывает**, а не ждёт.

Подробнее - в [Что Funora сегодня не может](../limits.md).
