# Диалоги и переписка

## Список диалогов

```python
from funora import Client, EnvSecretProvider

with Client(EnvSecretProvider()) as client:
    page = client.chats.list()

    for chat in page.rows():
        print(chat.node_id, chat.counterparty_name.or_none(), chat.unread)
```

| Поле | Что это |
|---|---|
| `node_id` | идентификатор диалога, им зовутся остальные операции |
| `counterparty_name` | имя собеседника |
| `preview_text` | последняя строка, как показана в списке |
| `unread` | диалог непрочитан |
| `time_text` | время последнего сообщения, текстом |
| `last_message_position`, `own_position` | служебные метки порядка |

!!! warning "`unread` - выведенный признак, а не наблюдённый"

    Он получен из расхождения двух позиций в строке диалога, а расхождения при
    непрочитанном диалоге не наблюдалось ни разу: снимка списка с
    непрочитанным диалогом у проекта нет.

    Поэтому у него уверенность `Confidence.INFERRED` - и это видно в самом
    значении:

    ```python
    from funora import Confidence

    if chat.unread.confidence is Confidence.INFERRED:
        ...  # правило выведено рассуждением, а не увидено
    ```

    Закрывается это одним снимком списка с непрочитанным диалогом - см.
    [открытые вопросы](../protocol-questions.md).

## Переписка

```python
from funora import Client, EnvSecretProvider, Origin

with Client(EnvSecretProvider()) as client:
    thread = client.chats.thread("123456")

    for message in thread.messages():
        who = "площадка" if message.origin is Origin.SYSTEM else "человек"
        print(who, message.author_name.or_none(), message.text.or_none())
```

Записи достаются методом `messages()`, а не `rows()` - переписка это не список
строк таблицы, - но правила те же: при неполноте нужен явный
`accept_incomplete=True`.

### Происхождение сообщения

```python
from funora import Origin

Origin.HUMAN    # написал человек
Origin.SYSTEM   # написала площадка
Origin.UNKNOWN  # не определено
```

Различать это важно: сообщение площадки об оплате выглядит как обычное
сообщение в диалоге, и обработчик, читающий подряд, примет его за слова
покупателя.

!!! danger "Сообщение площадки не подтверждает оплату"

    Даже верно опознанное системное сообщение подтверждением не является: оно
    могло относиться к другому заказу, устареть или прийти по платежу, который
    потом отменили.

    Площадка предупреждает об этом сама - первым сообщением в каждом диалоге.
    Источник истины про деньги один: [список продаж](orders.md).

### Ссылки наружу

```python
for message in thread.messages():
    if message.external_links:
        print("в сообщении есть ссылки на чужие хосты:", message.external_links)
```

Поле собирается разбором, а не доверием к тексту: ссылка на чужой хост в
сообщении от «поддержки» - самый обычный способ увести аккаунт.

## Отметка прочтения

```python
from funora import Capability, Client, EnvSecretProvider

with Client(
    EnvSecretProvider(),
    experimental={Capability.CHATS_MARK_READ},  # (1)!
) as client:
    client.chats.mark_read("247450736")  # (2)!
```

1. **Обязательно.** Без согласия операция откажет **до** обращения к сети.
2. Возвращает `None`, и это не упущение - см. ниже.

!!! info "Отдельного запроса у этого действия нет вовсе"

    Три недели мы ждали наблюдения запроса отметки прочтения. Наблюдать было
    нечего: такого запроса не существует.

    Диалог помечается прочитанным тем, что его узел попал в **подписку** обычного
    опроса канала обновлений. Страница, открыв переписку, опрашивает канал с
    объектом `chat_node` и пустым содержимым - подписка эта и есть всё действие.

### Почему спрашивается согласие

Форма запроса - **наша**: наши записи показывают этот опрос десятками.

Вывод о том, что именно подписка снимает пометку непрочитанного, - **чужой**, от
независимой реализации того же протокола. Проверить его мы не могли:
непрочитанность видна у **покупателя**, а не у нас.

Отменить действие тоже нельзя - пометить диалог непрочитанным обратно площадка не
предлагает нигде.

### Подтверждения нет, и оно не выдумывается

Метод возвращает `None`. Ответ канала несёт состояние подписанных объектов, а
пометка непрочитанного видна не нам; вернуть отсюда «готово» значило бы сообщить
об исполнении, ничего о нём не зная.

!!! danger "Отправка текста делает то же самое побочно"

    `client.chats.send_text(...)` кладёт в подписку **тот же объект** - иначе
    ответ канала не подтвердит отправку, канал подтверждает только подписанное.

    Значит **всякая отправка попутно помечает переписку прочитанной**. Отправить,
    не пометив, нельзя: без подписки исход отправки не подтверждается ничем, а
    неподтверждённая отправка хуже помеченной переписки.

    Объявлено вслух с 31.08.2026. Прежде действие происходило и молчало:
    автоответчик снимал пометку непрочитанного у покупателя, а его хозяин об этом
    не знал.

## Отправка изображения

```python
result = client.chats.send_image(
    "247450736",
    Path("снимок.png").read_bytes(),
    filename="снимок.png",
)
print(result.outcome)
```

Согласия эта операция **не спрашивает**, и это не оплошность: обе её половины -
загрузка файла и отправка номера - наблюдены нами. Спрашивать согласие там, где
чужого знания нет, значило бы обесценить сам механизм.

### Два шага

Файл уходит отдельным обращением и получает взамен **номер**. Затем номер
отправляется обычным действием канала - тем же, что и текст, но с `image_id`
вместо содержимого.

!!! danger "Нет номера - нет и второго запроса"

    Если ответ на загрузку не несёт номера, операция отказывает и **не
    отправляет ничего**.

    Выдуманный номер отправил бы покупателю **чужой файл** - чей угодно, лежащий
    у площадки под этим номером. Это хуже неотправки на порядок.

### Предел размера читается со страницы

Площадка объявляет наибольший размер файла в настройках самой страницы. Операция
читает его оттуда и **не заводит своего**: свой предел отверг бы то, что
площадка приняла бы, - и отверг бы молча, на нашей стороне, где вам нечего
возразить.

Предела на странице не оказалось - файл уходит как есть. Отсутствие объявления
не повод для догадки.

Побочное действие то же, что у отправки текста: переписка помечается
прочитанной.

## Что покупатель смотрит прямо сейчас

```python
for one in client.chats.buyer_viewing("247450736", "9310582"):
    if one.viewing:
        print(one.buyer_id, "смотрит", one.lot_text.or_none(), one.lot_href.or_none())
    else:
        print(one.buyer_id, "не смотрит ничего")
```

Страница диалога нужна не ради диалога, а ради защитного токена: без него к каналу
не обратиться вовсе.

!!! info "Порядок ответа - спрошенный, а не полученный"

    Канал перечисляет объекты как попало. Сопоставив записи по месту, вы
    получили бы **чужого** покупателя - и показали бы продавцу, что не тот
    смотрит его лот.

    Не ответивший получает наблюдение «не смотрит», а не пропадает из перечня.

### Раскол наблюдения

**Подписка наша**: объект этого вида лежит в семи наших записях канала, и состав
её известен - признак, идентификатор, метка.

**Ответ на неё мы не видели ни разу.** Что приходит внутри, известно от
независимой реализации того же протокола.

Отсюда два следствия, которые стоит знать:

- **разметка блока сохраняется как есть** в `raw_html`. Не разберись `lot_href` и
  `lot_text` - у вас останется то, из чего вы поймёте сами;
- **всё непонятное читается как «не смотрит»**, а не как поломка. Ответа мы не
  видели, и объявлять поломкой непредвиденное значило бы ломать чтение у
  операции, которую зовут в цикле опроса.

`viewing=False` - это **наблюдение**: площадка сказала «не смотрит». Неудачу
чтения выражает отказ, а не ложь в поле.

## Что здесь ещё не работает

Дочитывание переписки назад (`chats.history_before`) объявлено контрактом и не
написано.

Позвав его, вы получите `NotImplementedOperationError` - отказ **самой Funora**,
а не встроенную ошибку Python. Разница практическая: общий перехват
`FunoraError` его поймает, и остановится операция, а не весь ваш цикл.

Отправка текста - работает, и ей посвящена [отдельная глава](sending.md).
