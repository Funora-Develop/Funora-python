# Темп и бюджет

У площадки нет опубликованных пределов, и узнать их можно ровно одним способом -
превысить. Проект этого не делает нарочно: намеренно провоцировать ограничение
значит рисковать чужим аккаунтом ради числа в документации.

Поэтому все числа здесь **предварительные** и выбраны в сторону осторожности.

```python
import funora.budget as budget

print(budget.PROVISIONAL)  # True: числа предварительные
```

## Точность ожидания

Бюджет хранит запас, право на залп и доли точными десятичными значениями.
Промежуточные проверки не накапливают погрешность. Округляется только готовая
пауза: целая часть миллисекунд плюс защитная миллисекунда при нехватке запаса.
Например, после пяти одновременных запросов одного аккаунта следующие уходят
через 201, 401 и 601 мс от начала. Это расчёт по виртуальным часам; настоящие
таймеры и сеть могут задержать отправку дольше.

Неконечные время и стоимость, а также отрицательная стоимость отвергаются до
изменения бюджета. Нулевая стоимость допустима, в том числе для отдельного
учёта действия записи. Значения лимитов остаются предварительными.

## Два разных ограничителя

Их легко перепутать, а устроены они по-разному.

**Бюджет запросов** считает обращения к площадке - любые. Он про то, чтобы вас
не приняли за нагрузку.

**Ограничитель исходящих** считает отправленные сообщения и собеседников. Он про
то, чтобы вас не приняли за рассылку. Про него - в главе
[Отправка](sending.md).

## Бюджет запросов

Запрос проходит через общее сетевое и персональное ведро:

| Ведро | Ёмкость | Пополнение | Про что |
|---|---|---|---|
| `host` | 60 | 1/с | нагрузка на площадку целиком |
| `account` | 30 | 0.5/с | нагрузка от одного аккаунта |


!!! note "Двадцать аккаунтов в одном процессе не дают двадцати залпов"

    Ведро хоста общее. Это нарочно: площадке всё равно, сколько у вас аккаунтов,
    ей видна суммарная нагрузка.

Для нескольких аккаунтов задавайте устойчивый `account_id` при создании
`Client` или `AsyncClient`. Одинаковый ключ на одной сетевой идентичности
делит одну персональную квоту; разные ключи получают разные квоты под общим
сетевым пределом. Значение по умолчанию `self` объединяет клиентов без ключа
в одну квоту. Это ключ планирования, а не подтверждение авторизации.

Публичные `market.offers`, `market.snapshot` и `market.chips` делят свою квоту,
но тот же сетевой предел. Перенос чтения в публичную полосу не удваивает
разрешённую нагрузку и не обходит паузу после HTTP 429.

## Квота действий записи

Ведро `write` подключено ко всем 11 операциям записи. Оно общее для сетевой
идентичности: разные аккаунты одного выхода не получают отдельные залпы записи.
Перед первым изменением SDK атомарно резервирует сетевые квоты и одно действие.
Отказ любого ведра не расходует другие.

Загрузка изображения и отправка сообщения считаются одним действием и двумя
HTTP-запросами. Подготовительное чтение, безопасный POST, непригодный ввод и
вызов без сохранения ничего в `write` не списывают. При неизменной строке цены
или уже установленной видимости лот не сохраняется повторно.

Если изменение началось, потерянный ответ не возвращает действие в квоту:
результат на площадке может быть уже применён. Ограничитель сообщений и аудит
цены остаются дополнительными проверками перед запросом.

Ёмкость `write` - 60 действий, пополнение - 0,0167 в секунду, залп - 5.
Это ведро токенов, а не жёсткое скользящее окно «60 за любой час»: после простоя
доступен накопленный запас плюс дальнейшее пополнение. Числа предварительные.
Состояние хранится в памяти общего runtime и сбрасывается при перезапуске;
долговечный журнал сообщений продолжает действовать отдельно.

По умолчанию `Budget()` включает `host`, `account` и `write`. Явный список
`names` заменяет этот набор; `Budget(names=())` отключает все три квоты и
предназначен для контролируемых тестов. При прямой работе с бюджетом только
первый запрос изменения вызывает `reserve(..., action=True)` или
`require(..., action=True)`. Параметр `cost` по-прежнему задаёт сетевой расход.

## Что происходит при исчерпании

Зависит от того, чем вызван запрос:

```python
from funora.budget import ON_REFUSAL, RequestClass

ON_REFUSAL[RequestClass.INTERACTIVE]  # wait
ON_REFUSAL[RequestClass.MONITORING]   # refuse
```

Запрос, вызванный действием человека, **ждёт**: человек предпочтёт подождать
секунду, а не увидеть ошибку. Запрос мониторинга **отказывает**: он повторится
сам через минуту, и держать его в очереди незачем.

Ожидание не бесконечно. Дождавшись предела, запрос отказывает с
`BudgetExhaustedError`, и в отказе сказано, сколько ждать.

## Свой бюджет

```python
from funora import Budget, Client, EnvSecretProvider

with Client(EnvSecretProvider(), budget=Budget()) as client:
    ...
```

Общий бюджет на несколько клиентов - штатный случай: так ведро хоста считает
всех вас вместе.

## Приостановка

Получив от площадки ответ об ограничении, SDK приостанавливает бюджет сам, на
объявленный срок. Спросить об этом:

```python
from time import monotonic

from funora import Budget
from funora.budget import RequestClass

my_budget = Budget()

if my_budget.is_suspended(RequestClass.MONITORING, monotonic()):
    ...
```

## Пределы отправки

| Что | Значение |
|---|---|
| сообщений в час | 30 |
| разных собеседников в час | 15 |
| холодных обращений | 3 в сутки |
| пауза между сообщениями в одну переписку | 30 секунд |

Порядок проверки объявлен и нормативен: сперва ошибка вызывающего, потом узкие
пределы, потом широкие. Так названный в отказе предел - самый близкий к
разрешению из упёршихся, а не первый попавшийся.

Попытки отправки сохраняются в `state_path` до сетевого запроса, под блокировкой
процессов. Перезапуск восстанавливает счётчики. Без файла состояния отправка
отказывает; явное послабление `unsafe_sends_without_ledger=True` снимает защиту
от сброса при перезапуске. Подробности - в главе [Отправка](sending.md).

## Часы

Ни бюджет, ни ограничитель не смотрят на часы сами - время приходит к ним
аргументом. Это выглядит неудобно и сделано ради одного: такую логику можно
проверить, не ожидая настоящих секунд.

Заодно решается неприятность, о которой обычно вспоминают поздно: перевод
системных часов. Внутри одного запуска счёт идёт по монотонным часам, которые не
прыгают от синхронизации времени, а на диск метки пишутся стенные - монотонное
показание после перезапуска не значит ничего.
