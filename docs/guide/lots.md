# Лоты и витрина

Три страницы площадки показывают лоты, и это три разные страницы с разными
данными. Путать их дорого.

| Что | Метод | Чьи лоты | Зачем |
|---|---|---|---|
| Свои лоты в разделе | `client.lots.list_own(node_id)` | ваши | **идентификатор предложения** |
| Витрина продавца | `client.lots.showcase(user_id)` | чьи угодно | больше полей, но без идентификатора |
| Публичный список раздела | разбор есть, операции нет | всех продавцов | цены конкурентов |

## Свои лоты

```python
from funora import Client, EnvSecretProvider

with Client(EnvSecretProvider()) as client:
    page = client.lots.list_own("1234")

    for lot in page.lots():
        print(lot.offer_id.value, lot.price_text.or_none(), lot.description_text.or_none())
```

Записи достаются методом `lots()`.

### Зачем она, когда есть витрина

Витрина показывает те же лоты и даже **больше** полей - количество и признак
автовыдачи. Не даёт она одного: **идентификатора предложения**. Там он спрятан
в строке запроса ссылки.

Здесь он лежит атрибутом строки. Идентификатор нужен всем операциям записи над
лотами - а значит, эта страница нужна раньше, чем они будут написаны.

### Чего в записи нет

**Признака «лот показывается в выдаче».** Его на странице нет ни одного: все
строки структурно одинаковы, различающего класса нет, переключателя у строки нет.

Поле не выдумано нарочно. Выдумать его значило бы сказать продавцу «лот скрыт»
о показанном либо наоборот.

!!! note "Узел с говорящим именем им не является"

    В разметке есть `.tc-visible-inside`, и по имени это похоже на признак
    видимости. Это не он: тот же класс есть на **публичной** витрине профиля,
    которую видит любой посетитель. Наличие определяется набором колонок, а не
    состоянием лота.

### Показывается ли лот

```python
page = client.lots.list_own("922")
for lot in page.lots():
    print(lot.offer_id.or_none(), "показан" if lot.is_active else "ВЫКЛЮЧЕН")
```

Читается наличием класса `warning` у строки: включённая его не несёт вовсе.

!!! warning "Что класс означает - известно наполовину"

    Наблюдался **один** способ его получить: снять галочку «Активное» в форме
    правки. Класс общий по имени, и площадка вправе красить им и другое -
    истёкший срок, нехватку остатка, отказ модерации.

    Прочих способов не искали, и объявлять их отсутствие нельзя.

!!! note "Три недели этого поля здесь не было, и зря"

    Модель утверждала, что признака на странице нет вовсе. Строки одинаковы,
    пока все лоты включены, - а на снимке, по которому писали, все и были
    включены.

    Отсутствие признака на однородном снимке не значит его отсутствия на
    странице. Проверить стоило одним опытом: выключить лот и посмотреть.

### Кнопка поднятия

```python
page = client.lots.list_own("1234")
print(page.raise_game_id.or_none(), page.raise_node_id.or_none())
```

Это данные кнопки «поднять лоты», лежащие на странице. Самой операции поднятия
нет: запроса, которым она делается, никто не наблюдал. Данные объявлены затем,
чтобы наблюдение поднятия не пришлось делать вслепую.

## Правка цены

Первая операция записи над лотами. Работает так:

```python
from funora import Client, EnvSecretProvider

with Client(EnvSecretProvider(), state_path="funora-state.json") as client:
    form = client.lots.form("1908", "75289502")  # (1)!

    print(form.price_text, form.currency_symbol.or_none())
    print("показан:", form.is_active)  # (2)!

    if form.is_active:
        after = client.lots.update_price(
            "1908", "75289502", "2.50",
            expected_revision=form.revision,  # (3)!
        )
        print("стало:", after.price_text)
```

1. Раздел и предложение. Идентификатор предложения берётся из
   `client.lots.list_own(node_id)`.
2. **Единственное место, где виден признак показа лота в выдаче.** На странице
   своих лотов его нет ни одного, и `Lot` из-за этого не собирался вовсе.
3. **Обязателен.** Без него параллельная правка - из другого процесса, из
   приложения, из веб-интерфейса - была бы перетёрта молча.

### Отправляется прочитанное

Форма несёт подробное описание лота, сообщение покупателю после оплаты и
картинки. Операция читает её целиком и отправляет обратно, меняя **ровно одно
поле**.

Собрать запрос из перечня нужных полей было бы короче и стёрло бы всё
остальное - а узнал бы об этом продавец глазами, из своей же витрины.

### Отпечаток - наш, а не площадкин

Площадка версии лота не даёт нигде. Поэтому `revision` - отпечаток самих
значений: изменилось что угодно, изменился отпечаток.

Он слабее настоящей версии в одном: правка, вернувшая прежние значения,
отпечатка не меняет. И сильнее в другом: замечает правку любого поля, а не
только объявленных.

Токен и метку сборки формы отпечаток не считает - они меняются при каждом
чтении страницы, и иначе правка отказывала бы всегда.

!!! danger "Выключенный лот операция не трогает"

    Что уходит при **снятом** флажке, никто не наблюдал. Отправив форму, мы
    отправили бы флажок отмеченным - то есть включили бы лот, которого не
    просили включать.

    Поэтому на выключенном лоте `update_price` отказывает. Включения и
    выключения по той же причине пока нет вовсе.

### Успех виден переходом

Тела ответа страница не получает: сохранение уходит переходом, и ответ
забирает браузер. Успех - переход на список своих предложений раздела;
приведи сохранение куда-то ещё, операция откажет, а не объявит успех.

### Журнал правок обязателен

`state_path` в примере выше - не удобство. **Без него правка цены отказывает.**

```python
from funora import Client, EnvSecretProvider

with Client(EnvSecretProvider()) as client:  # без state_path
    client.lots.update_price(...)
    # ConfigurationError: правка цены отказывает без долговечного журнала
```

Довод короткий: у площадки нет ни истории цен, ни отката. Вернуть как было
можно только по **нашей** записи, а запись в памяти процесса перезапуск стирает
целиком.

Запись ложится в файл **раньше**, чем уходит запрос. «Запишем, когда
подтвердится» означает не записать ровно те правки, которые могли уйти: ответ
теряется, процесс падает, а цена на площадке уже новая.

```python
audit = client.engine.price_audit

was = audit.original("75289502")  # (1)!
print(was.price_before if was else "лот не трогали")

for one in audit.history("75289502"):  # (2)!
    print(one.at_ms, one.price_before, "->", one.price_after)

print("вытеснено записей:", audit.dropped)  # (3)!
```

1. Первая правка лота - та самая цена, что стояла **до бота**. Она не
   вытесняется никогда.
2. Все правки по порядку, от старой к новой.
3. Журнал ограничен пятью сотнями записей: переоценщик, ходящий раз в минуту,
   за год пишет полмиллиона. Вытесненные считаются - молчаливое усечение
   читалось бы как «правок было столько».

!!! warning "Послабление есть, и оно оставляет след"

    `unsafe_price_changes_without_audit=True` снимает отказ. Отметка
    `unsafe_price_changes_without_audit` встаёт в `SessionHealth.unsafe_marks`:
    снять защиту можно, снять её незаметно нельзя.

    Цена послабления - потерянная прежняя цена. Не заплатив её однажды,
    заплатить придётся ошибкой переоценщика, которую нечем отменить.

### Две возможности, а не одна

У чтения формы и у правки цены **разные** возможности, и спрашиваются они порознь:

```python
from funora.capabilities import Capability

print(client.capability(Capability.LOTS_FORM))          # можно ли смотреть
print(client.capability(Capability.LOTS_UPDATE_PRICE))  # можно ли менять
```

Страницы две - `/lots/offerEdit` и сохранение, - и отвечать на них площадка
вправе по-разному. Обнаружив, что менять цену нельзя, вы сохраняете право
посмотреть, что у лота стоит сейчас.

Начальное состояние обеих - `unknown`, и это не «нельзя»: состояние выставляется
только по полученному ответу. `supported` появляется после первого удачного
чтения либо сохранения.

```python
with Client(EnvSecretProvider()) as client:

    print(page.sections_total, page.offers_total)
    for section in page.sections():
        ...
```

Витрина устроена разделами, а не плоским списком, и у неё своя мера полноты:
`capped_sections` - разделы, показанные не целиком.

## Публичный список раздела

Разбор написан и проверен, **операции нет**. Причина не в лени.

`market.offers` объявлена контрактом возвращающей `Offer[]`, а `Offer` требует
обязательными идентификатор, цену и раздел. Ни одного из трёх со страницы не
собрать: идентификатор чужого предложения лежит в строке запроса ссылки, цена
наблюдается текстом, а валюта не наблюдается вовсе.

Собрать `Offer` из того, что есть, значило бы выдумать три обязательных поля из
пяти.

!!! warning "Ловушка, ради которой эта страница вообще разбиралась"

    У строки списка есть атрибут `data-user`. По имени - продавец. На деле он
    есть у строки **тогда и только тогда, когда предложение поднято**.

    Разбор по нему отдал бы продавца у поднятых предложений и промолчал бы про
    все остальные - и выглядел бы работающим: поля заполняются, ошибок нет, а
    поднятые предложения показываются первыми и попадают в глаза первыми.

    Настоящий продавец лежит в другом атрибуте, у аватара внутри строки.

Разбором можно пользоваться напрямую, если вы понимаете, что делаете:

```python
from funora._market import parse_market  # (1)!
```

1. Модуль приватный, и имя начинается с подчёркивания не случайно: это не часть
   публичного API, и меняться он может без предупреждения.
